# Skill Generator Skill

# 1. Name

The first section of every Skill must define its name.

The name must be:

- Short
- Clear
- Unique
- Representative of the Skill's purpose.

Examples:

```text
Hexagonal Architecture Skill

GraphQL Skill

Security Skill

Testing Skill
```

---

# 2. Description

The second section must define the scope of the Skill.

It must clearly explain:

- What the Skill defines.
- What responsibilities it owns.
- What it establishes.
- What it explicitly does not define.

The description defines the boundaries of the Skill and prevents responsibility overlap with other Skills.

Recommended format:

```text
This Skill defines...

This Skill establishes...

This Skill does not define...
```

---

# 3. General Rules

After the Description, all global rules must be defined.

General Rules contain only rules that affect the entire Skill.

This section must never describe a specific folder or file.

Examples:

- objectives
- architectural principles
- dependency direction
- conventions
- standards
- naming conventions
- restrictions
- generation rules
- validations
- checklists
- best practices

If a rule affects multiple components, it belongs here.

If a rule affects only one component, it belongs inside that component's section.

---

# 4. Project Structure

This section defines only the complete physical structure generated by the Skill.

It must contain only the generated structure.

It must not describe:

- responsibilities
- implementation
- behavior
- dependencies
- architectural decisions

Its only purpose is to describe the generated structure.

Example:

```text
src

└── company
    ├── application
    ├── domain
    └── infrastructure
```

After reading this section, the complete generated structure must be understood.

---

# 5. Component Sections

After the project structure has been defined, every important architectural component must have its own dedicated section.

A component may be:

- a directory
- a file

Every component owns exactly one section.

No two sections may describe the same component.

---

# Component Types

There are two kinds of components.

## Directory Components

A directory component defines part of the project architecture.

Examples:

```text
domain

application

infrastructure

platform

persistence
```

Directory components explain:

- why the directory exists
- what it contains
- what it must never contain
- its internal organization
- its architectural responsibilities

---

## File Components

A file component defines the behavior of a specific file.

Examples:

```text
JwtGenerator.java

KeyGenerator.java

CompanyGraphQLApi.java

SecurityConfiguration.java
```

Every mandatory generated file must have its own dedicated section.

File components explain:

- why the file exists
- what it does
- how it behaves
- what responsibilities it owns
- what dependencies it may use
- what restrictions apply

---

# Component Section Template

Every component section should follow the same structure.

```text
# X. Component Name

Location

Ownership

Purpose

Responsibilities

Internal Structure

Dependency Rules

Allowed Content

Forbidden Content

Restrictions

Examples
```

Not every subsection is mandatory.

Each Skill should include only the subsections required to describe that component.

---

# Location

Every component section must begin by indicating its physical location.

Example:

```text
Location

src/main/java/...
```

The location must never be part of the section title.

It must appear immediately after the title.

---

# Ownership

Every component must define exactly what it owns.

Ownership makes that section the only source of truth for that component.

Example:

```text
Ownership

This section is the only source of truth for:

- Responsibilities
- Dependencies
- Internal organization
- Allowed content
- Forbidden content
```

No other section may redefine these responsibilities.

---

# Purpose

Purpose explains why the component exists.

It answers:

> Why does this component exist?

Purpose describes intention.

It does not describe implementation.

---

# Responsibilities

Responsibilities define exactly what the component does.

Only responsibilities belonging to that component should appear here.

Responsibilities from other components must never appear here.

---

# Internal Structure

If the component contains relevant child components, they should be described using subsections.

Example:

```text
## model

...

## valueobject

...

## port
```

Subsections must never be numbered.

---

# Dependency Rules

Defines only the dependencies of the current component.

Example:

Allowed:

```text
Application → Domain
```

Forbidden:

```text
Domain → Infrastructure
```

---

# Allowed Content

Defines what may exist inside the component.

Example:

```text
- DTOs
- Services
- Mappers
```

---

# Forbidden Content

Defines what must never exist inside the component.

Example:

```text
- Business logic
- Framework annotations
- Repository implementations
```

---

# Restrictions

Contains rules specific to the component.

Examples:

- architectural restrictions
- dependency restrictions
- implementation restrictions
- forbidden annotations
- generation rules

Only rules belonging to that component should appear here.

---

# Examples

Examples should be included only when they improve understanding.

Examples complement the rules.

They never replace the rules.

---

# Component Ownership Rule

Each component must have exactly one owner section.

That section is responsible for defining:

- purpose
- responsibilities
- dependencies
- restrictions
- internal organization
- allowed content
- forbidden content

No other section may redefine those rules.

---

# Single Source of Truth Rule

Every component must be defined exactly once.

If a rule belongs to a component, it must exist only inside that component's section.

Duplicated rules are not allowed.

---

# Section Responsibility Rule

Each section must have exactly one responsibility.

A section must never describe multiple unrelated components.

A component must never be described by multiple sections.

---

# Ordering Rules

Every Skill must always follow the same organization.

```text
# 1. Name

# 2. Description

# 3. General Rules

# 4. Project Structure

# 5. Component Sections
```

Component sections must never appear before the Project Structure.

---

# Numbering Rules

Every main section must be numbered.

Example:

```text
# 1.

# 2.

# 3.
```

Subsections must never be numbered.

Example:

```text
# 15. Domain

## model

## valueobject

## port
```

---

# Traceability Rule

Every important component must be defined exactly once.

If the generated implementation of a component is incorrect, it must be immediately possible to identify the responsible section and modify only that section.

This guarantees complete traceability between the Skill and the generated project.

---

# Modularity Rule

Every component must evolve independently.

Updating one component should never require modifying another section describing the same component.

Each responsibility must exist in exactly one location.

---

# Consistency Rule

All component sections should follow the same internal organization whenever possible.

Using a consistent structure makes the Skill easier to read, maintain, extend and debug.

New components should follow the same template instead of introducing different organizational patterns.

---

# Maintainability Rule

The Skill must be organized to maximize long-term maintainability.

A developer should always know:

- where a component is defined
- which section owns it
- where to modify its behavior
- which rules affect it

The organization of the Skill should minimize duplicated information while maximizing discoverability.

---

# Extensibility Rule

Skills should be designed to allow new components to be added without reorganizing existing sections.

New directories and files should be introduced simply by creating a new Component Section following the same template.

The overall organization of the Skill should remain stable as the project grows.
