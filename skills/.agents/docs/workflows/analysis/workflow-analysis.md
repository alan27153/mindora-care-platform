    Documento Técnico de Análisis y Especificación de Migración (spec.md)Este documento ha sido generado siguiendo de forma estricta las directrices de la skill de análisis de workflows de n8n (09-N8N-Backend-Migration-Skill). Contiene el análisis exhaustivo de los 94 nodos identificados en el workflow "waha". Sirve como la especificación definitiva y autocontenida para la migración hacia el backend Java Quarkus.Workflow SummaryEl workflow "waha" actúa como el motor de orquestación conversacional multicanal (WhatsApp y Web) para JOY IT. Registra entradas de clientes, gestiona estados de conversación, valida datos para cotización de proyectos mediante agentes de IA y RAG (Supabase Vector Store), controla cuotas/bloqueos de usuarios por consumo de tokens y deriva la atención a asesores humanos mediante la creación e historial de tickets.Total de Nodos Analizados: 94 nodos (100% inventariados y categorizados).Decisión de Migración: 76 Nodos migran al backend (Quarkus) y 18 Nodos permanecen en n8n (servicios de mensajería y adaptación directa de la API WAHA/WhatsApp).Nodos Deshabilitados: Ninguno (disabled: false en la totalidad del workflow).Complejidad: Alta (Orquestación RAG, agentes conversacionales con LangChain, control de estado en PostgreSQL, bifurcaciones por intentos fallidos y cuotas de tokens).Workflow OverviewDominio de Negocio: Asistencia virtual para cotización de servicios de desarrollo de software, soporte al cliente y captura de leads para JOY IT.Propósito: Atender consultas entrantes, identificar la intención del cliente, evaluar datos faltantes para cotización, consultar la base de conocimiento vectorial para respuestas asistidas y gestionar tickets en PostgreSQL.Canales Atendidos:WhatsApp: Integrado a través del conector WAHA (WhatsApp HTTP API).Web Chat: Atendido históricamente vía webhooks sincrónicos en n8n (Webhook1), cuya responsabilidad migra 100% al controlador REST de Quarkus (@POST /api/v1/chat).Servicios Integrados:Modelos de Lenguaje: OpenRouter (qwen/qwen3-235b-a22b), Groq (llama-3.3-70b-versatile, llama-3.1-8b-instant).Embeddings & Vector Store: Google Gemini Embeddings (text-embedding-004), Supabase Vector Store.Base de Datos Persistente: PostgreSQL (Tablas: clients, tickets, inquiries, conversation_metric, n8n_chat_histories).Actores: Cliente Final (WhatsApp/Web), Sistema Backend (Quarkus + n8n Adapter), Asesor Humano (Atención de tickets escalados).Execution FlowEl flujo principal se divide en 3 macro-procesos: Normalización y Evaluación de Límite, Procesamiento de Estado / Cotización, y Agente Conversacional RAG con Derivación a Ticket.Fragmento de códigoflowchart TD
